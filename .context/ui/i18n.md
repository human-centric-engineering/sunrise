# Interface languages

How a screen is shown in a language other than English (§138). Every string
an org's users and public visitors see comes from a catalogue, looked up in
the language the request resolves to.

**Status (t-1072):** the library, the catalogue, the resolution, the
storage and the app seam (its own strings and languages) are in place.
Moving the platform's screens and emails onto the catalogue is t-1073,
t-1074 and t-1075. Until those land, most screens are still literal English.

## Don't

- **Don't call `toLocaleDateString()`, `toLocaleString()` or `new
Intl.*Format()` in a screen.** They use the server's locale and time zone,
  not the viewer's. Use `getFormatter()` / `useFormatter()` and the named
  formats below.
- **Don't hand-edit or commit a pseudo-locale file.** `en-XA` is generated
  from `en` when the catalogue loads.
- **Don't put the locale in the URL.** There is no i18n routing: a prefix
  would move every route a fork owns and the `/admin` check in
  `lib/app/surface.ts`.
- **Don't add a locale by editing `PLATFORM_LOCALES`.** Sunrise ships `en`
  and `en-XA` only (owner ruling, §138 planning). A real language comes from
  an app, through the catalogue seam (`lib/app/messages.ts`, below).
- **Don't add a top-level `app` or `framework` namespace to `en.json`.**
  Both are reserved for downstream tiers' own strings
  (`APP_MESSAGE_NAMESPACES`), which is what keeps an app's strings from ever
  colliding with an upgrade. A test fails if the platform ships either.
- **Don't read `User.locale` or `Org.settings.locale` to pick a language
  yourself.** Ask next-intl (`getLocale()`) on a page, so every screen agrees
  with the resolution below.

## Which language a request gets

The first step that names a supported locale wins:

1. the signed-in user's own choice, `User.locale`;
2. the default of the org the request acts in, `Org.settings.locale` (the
   org the guards entered, so a support session gets the org it is in);
3. the visitor's cookie, `sunrise_locale`;
4. the browser's `Accept-Language`, in its order of preference;
5. `en`.

A regional request is served by its base language (`fr-CA` by `fr`), never the
other way round. Nothing reaches `en-XA` unless it is asked for by name. A
stored tag with no catalogue (a locale an app stopped registering) is skipped,
not trusted, so the next step answers.

The user's time zone (`User.timezone`, `UTC` when unset or unknown to `Intl`)
goes into the same config, so dates read in the viewer's zone.

## Setting it

| Who            | How                                                               | Guard                                                                                                |
| -------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| A user         | `PATCH /api/v1/users/me` `{ locale: string \| null }`             | Their own session                                                                                    |
| An org's admin | `PUT /api/v1/orgs/[id]/locale` `{ locale: string \| null }`       | The policy (OWNER/ADMIN acting in it); no API key or support session; audited as `org.locale.update` |
| A visitor      | `PUT /api/v1/locale` `{ locale: string \| null }` sets the cookie | Public                                                                                               |

`null` clears the choice, so the next step decides. Every write validates the
tag against `supportedLocales()`. Members read the org's default on
`GET /api/v1/orgs/[id]` as `settings.locale`.

## Writing a string

```tsx
// Server Component
import { getTranslations, getFormatter } from 'next-intl/server';

const t = await getTranslations('common');
const format = await getFormatter();
<p>
  {t('save')} · {format.dateTime(createdAt, 'short')}
</p>;

// Client Component
import { useTranslations, useFormatter } from 'next-intl';
```

Keys are type-checked against `en.json` (`types/next-intl.d.ts`), so a typo
fails `npm run type-check`. Plurals, selects and rich text are ICU:
`"{count, plural, one {# item} other {# items}}"`.

Named formats: `dateTime` `short` (20 Nov 2026), `long`, `dateTime`, `time`;
`number` `decimal`, `percent`, `compact`. Money is
`format.number(n, { style: 'currency', currency })`.

## An app's own strings and languages

An app registers from `initAppMessages()` in `lib/app/messages.ts`, with the
functions in `lib/i18n/registry.ts`. The registry runs it once, lazily,
before the first catalogue or supported-locale read. Only the server reads
it, for catalogues and the locale schemas on API routes. Keep the registry
and `supportedLocales()` off the client, because they bring the catalogue, every
translation the app registers and the ICU parser. A client form checks only
a tag's shape (`isLanguageTag` from `lib/i18n/tags.ts`, which imports
nothing) and the route checks that the locale is supported. Client components
get their messages from the server.

| Call                                        | Does                                                                                                                    |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `registerAppMessages(locale, { app: … })`   | Adds the app's own strings in `en` or a registered locale. Top-level keys must be `app` (or `framework`, for that tier) |
| `registerAppLocale(tag, platformStrings)`   | Adds a language: supported at once, for users, orgs and visitors. `platformStrings` is the platform's strings in it     |
| `overridePlatformMessages(locale, strings)` | Replaces individual platform strings in `en` or a registered locale                                                     |

```ts
// lib/app/messages.ts
import appEn from '@/lib/app/messages/en.json'; // { "app": { "client": { "title": "Clients" } } }
import platformFr from '@/lib/app/messages/platform-fr.json'; // { "common": { "save": "Enregistrer" } }
import appFr from '@/lib/app/messages/fr.json';
import {
  overridePlatformMessages,
  registerAppLocale,
  registerAppMessages,
} from '@/lib/i18n/registry';

export type AppMessages = typeof appEn; // t('app.client.title') type-checks

export function initAppMessages(): void {
  registerAppMessages('en', appEn);
  registerAppLocale('fr', platformFr);
  registerAppMessages('fr', appFr);
  overridePlatformMessages('en', { common: { save: 'Save changes' } });
}
```

Then `const t = await getTranslations('app.client'); t('title')`.

**Merge order.** Each layer wins over the one before:

1. the source, `en`: the platform's strings, then the app's `en` strings,
   then the app's `en` overrides;
2. the locale's platform translations and the app's strings in it;
3. the locale's overrides.

The pseudo-locale is generated from the source, so it shows app strings and
`en` overrides too.

**A key a locale lacks** shows in English, per key. When that locale's
catalogue is built, the log gives the number of missing keys and names up to
20 of them, once per locale and count
(`i18n: strings missing from an app locale show in English`).

**A platform key the platform does not have** (retired in an upgrade, or a
typo) is dropped from a translation or override with a warning, not thrown,
so an upgrade that removes a string never takes a whole translation down.

**What throws**, and so rolls back every registration and leaves the
platform catalogue serving: a tag that is not a language tag, or a deprecated
one `Intl` renames (`iw`, use `he`); a later call that changes a string into a
group of strings or back; `en` or
`en-XA` passed to `registerAppLocale` (override those instead); strings for
the pseudo-locale, or for a locale not yet registered; a namespace other than
`app` / `framework` in `registerAppMessages`, or either of those anywhere
else; a value that is not an object of strings; a string that is not valid ICU
(`'Hi {name'`); a key with a `.` in it.
Tags are stored canonical (`pt-br` → `pt-BR`).

## Checking a screen

Set your own language to `en-XA` (`PATCH /api/v1/users/me`
`{ "locale": "en-XA" }`), or as a visitor `PUT /api/v1/locale`. Every catalogue
string then reads `[Åççéñţéð]`. Plain English left on the page did not come
from the catalogue. Text cut off before its `]` has no room to grow, and
real translations run longer than English.

## Rendering cost

Resolving the locale reads cookies, headers and the session, so rendering is
dynamic. That changed nothing: the root layout already read `headers()` for
the CSP nonce, so no page was static before.

It does add work to **every** page render, public and marketing pages
included: the root layout's `getLocale()` resolves the session and, for a
signed-in viewer, enters the org they act in (`requestPrincipal()`), then reads
their user row and that org's settings. All of it is cached for the request
and shared with anything else on the page that asks. A visitor with no session
cookie costs no database read. If the reads fail, the page still renders in the
browser's language and the log says `i18n: could not read the viewer's
language preferences`.

## The global error page is English

`app/global-error.tsx` replaces the root layout when that layout itself
throws, so the request config may be what failed. It renders its own
`<html lang="en">` with literal English on purpose, and stays that way: on
`en-XA` it is the one page expected to show plain English.
