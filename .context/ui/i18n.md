# Interface languages

How a screen is shown in a language other than English (§138). Every string
an org's users and public visitors see comes from a catalogue, looked up in
the language the request resolves to.

**Status (t-1071):** the library, the catalogue, the resolution and the
storage are in place. Apps registering their own strings and languages is
t-1072. Moving the platform's screens and emails onto the catalogue is
t-1073, t-1074 and t-1075. Until those land, most screens are still literal
English.

## Don't

- **Don't call `toLocaleDateString()`, `toLocaleString()` or `new
Intl.*Format()` in a screen.** They use the server's locale and time zone,
  not the viewer's. Use `getFormatter()` / `useFormatter()` and the named
  formats below.
- **Don't hand-edit or commit a pseudo-locale file.** `en-XA` is generated
  from `en` when the catalogue loads.
- **Don't put the locale in the URL.** There is no i18n routing: a prefix
  would move every route a fork owns and the `/admin` check in
  `lib/app/surface.ts`.
- **Don't add a locale by editing `PLATFORM_LOCALES`.** Sunrise ships `en`
  and `en-XA` only (owner ruling, §138 planning). A real language comes from
  an app, through the catalogue seam (t-1072).
- **Don't read `User.locale` or `Org.settings.locale` to pick a language
  yourself.** Ask next-intl (`getLocale()`) on a page, so every screen agrees
  with the resolution below.

## Which language a request gets

The first step that names a supported locale wins:

1. the signed-in user's own choice, `User.locale`;
2. the default of the org the request acts in, `Org.settings.locale` (the
   org the guards entered, so a support session gets the org it is in);
3. the visitor's cookie, `sunrise_locale`;
4. the browser's `Accept-Language`, in its order of preference;
5. `en`.

A regional request is served by its base language (`fr-CA` by `fr`), never the
other way round. Nothing reaches `en-XA` unless it is asked for by name. A
stored tag with no catalogue (a locale an app stopped registering) is skipped,
not trusted, so the next step answers.

The user's time zone (`User.timezone`, `UTC` when unset or unknown to `Intl`)
goes into the same config, so dates read in the viewer's zone.

## Setting it

| Who            | How                                                               | Guard                                                                                                |
| -------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| A user         | `PATCH /api/v1/users/me` `{ locale: string \| null }`             | Their own session                                                                                    |
| An org's admin | `PUT /api/v1/orgs/[id]/locale` `{ locale: string \| null }`       | The policy (OWNER/ADMIN acting in it); no API key or support session; audited as `org.locale.update` |
| A visitor      | `PUT /api/v1/locale` `{ locale: string \| null }` sets the cookie | Public                                                                                               |

`null` clears the choice, so the next step decides. Every write validates the
tag against `supportedLocales()`. Members read the org's default on
`GET /api/v1/orgs/[id]` as `settings.locale`.

## Writing a string

```tsx
// Server Component
import { getTranslations, getFormatter } from 'next-intl/server';

const t = await getTranslations('common');
const format = await getFormatter();
<p>
  {t('save')} · {format.dateTime(createdAt, 'short')}
</p>;

// Client Component
import { useTranslations, useFormatter } from 'next-intl';
```

Keys are type-checked against `en.json` (`types/next-intl.d.ts`), so a typo
fails `npm run type-check`. Plurals, selects and rich text are ICU:
`"{count, plural, one {# item} other {# items}}"`.

Named formats: `dateTime` `short` (20 Nov 2026), `long`, `dateTime`, `time`;
`number` `decimal`, `percent`, `compact`. Money is
`format.number(n, { style: 'currency', currency })`.

## Checking a screen

Set your own language to `en-XA` (`PATCH /api/v1/users/me`
`{ "locale": "en-XA" }`), or as a visitor `PUT /api/v1/locale`. Every catalogue
string then reads `[Åççéñţéð]`. Plain English left on the page did not come
from the catalogue. Text cut off before its `]` has no room to grow, and
real translations run longer than English.

## Rendering cost

Resolving the locale reads cookies, headers and the session, so rendering is
dynamic. That changed nothing: the root layout already read `headers()` for
the CSP nonce, so no page was static before. For a signed-in viewer it adds
one user and one org lookup per request, cached for the request.
