# Interface languages

How a screen is shown in a language other than English (§138). Every string
an org's users and public visitors see comes from a catalogue, looked up in
the language the request resolves to.

**Status (t-1075):** the library, the catalogue, the resolution, the
storage and the app seam are in place. Every user and public screen
(`app/(auth)`, `app/(public)`, `app/(protected)` and what they render) reads
from the catalogue, and so do the org-settings admin pages and the parts of
the admin shell an org admin sees on them (below). The rest of the admin
stays English by ruling. Every email in `emails/` is written in its
recipient's language, subject included (below).

## Don't

- **Don't call `toLocaleDateString()`, `toLocaleString()` or `new
Intl.*Format()` in a screen.** They use the server's locale and time zone,
  not the viewer's. Use `getFormatter()` / `useFormatter()` and the named
  formats below.
- **Don't hand-edit or commit a pseudo-locale file.** `en-XA` is generated
  from `en` when the catalogue loads.
- **Don't put the locale in the URL.** There is no i18n routing: a prefix
  would move every route a fork owns and the `/admin` check in
  `lib/app/surface.ts`.
- **Don't add a locale by editing `PLATFORM_LOCALES`.** Sunrise ships `en`
  and `en-XA` only (owner ruling, §138 planning). A real language comes from
  an app, through the catalogue seam (`lib/app/messages.ts`, below).
- **Don't write English into the JSX of a converted screen.** ESLint's
  `react/jsx-no-literals` rejects it on the converted paths (the block in
  `eslint.config.mjs`), wrapped or not. It cannot check props, so an
  `aria-label`, `placeholder` or `alt` is on you.
- **Don't build a form's schema from the exported constant.** Use its
  factory with the translator (below), or the field errors stay English.
- **Don't add a top-level `app` or `framework` namespace to `en.json`.**
  Both are reserved for downstream tiers' own strings
  (`APP_MESSAGE_NAMESPACES`), which is what keeps an app's strings from ever
  colliding with an upgrade. A test fails if the platform ships either.
- **Don't read `User.locale` or `Org.settings.locale` to pick a language
  yourself.** Ask next-intl (`getLocale()`) on a page, so every screen agrees
  with the resolution below. For an email, ask `lib/email/locale.ts`.
- **Don't write an email in the sender's language.** `getLocale()` in a
  route that sends mail is the language of whoever pressed the button, not
  of whoever receives it. Work it out from the recipient (below).

## Which language a request gets

The first step that names a supported locale wins:

1. the signed-in user's own choice, `User.locale`;
2. the default of the org the request acts in, `Org.settings.locale` (the
   org the guards entered, so a support session gets the org it is in);
3. the visitor's cookie, `sunrise_locale`;
4. the browser's `Accept-Language`, in its order of preference;
5. `en`.

A regional request is served by its base language (`fr-CA` by `fr`), never the
other way round. Nothing reaches `en-XA` unless it is asked for by name. A
stored tag with no catalogue (a locale an app stopped registering) is skipped,
not trusted, so the next step answers.

The user's time zone (`User.timezone`, `UTC` when unset or unknown to `Intl`)
goes into the same config, so dates read in the viewer's zone.

## Setting it

| Who            | How                                                                          | Guard                                                                                                |
| -------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| A user         | `PATCH /api/v1/users/me` `{ locale: string \| null }`                        | Their own session                                                                                    |
| An org's admin | Admin → Options; `PUT /api/v1/orgs/[id]/locale` `{ locale: string \| null }` | The policy (OWNER/ADMIN acting in it); no API key or support session; audited as `org.locale.update` |
| A visitor      | `PUT /api/v1/locale` `{ locale: string \| null }` sets the cookie            | Public                                                                                               |

`null` clears the choice, so the next step decides. Every write validates the
tag against `supportedLocales()`. Members read the org's default on
`GET /api/v1/orgs/[id]` as `settings.locale`.

Settings has the user's picker (`components/settings/language-form.tsx`);
the public footer has the visitor's switch
(`components/layouts/language-switch.tsx`), shown only to a visitor who is
not signed in, since a user's own choice outranks the cookie. Both get their
list from `localeOptions()` (`lib/i18n/locale-options.ts`, server-only):
each language named in itself, the pseudo-locale outside production only.

## The admin console

Owner ruling at §138 planning: the admin follows the viewer's language only
where an org's own admins work, which is the org-settings pages.

**Follows the viewer's language:** Members, Options, AI keys, Support access
and Waitlist (`app/admin/<page>` and `components/admin/<page>`); the
sidebar's chrome, its Management heading and those five items; the header's
breadcrumbs for those pages and "Acting in"; the locked page; the admin error
page.

**Stays English:** every staff-only page and nav item (Users,
Organisations, Feature Flags, Logs, the overview, the support banner), and
the orchestration console, its pages and its nav.

`tests/unit/components/admin/admin-language-scope.test.tsx` holds the line
under the pseudo-locale.

- **The sidebar translates by href.** `CATALOGUE_ITEMS` in
  `components/admin/admin-sidebar.tsx` maps the five items to `admin.nav`
  keys at render; `coreNavSections` keeps its English, so the roster tests
  and a fork's `registerNavSection()` see what they always saw. A fork's own
  nav labels, breadcrumb names (`lib/app/admin-breadcrumbs.ts`) and
  entitlement switch labels are its copy and show as given.
- **Options holds the org's language.** The picker
  (`components/admin/org-options/org-language-form.tsx`) is shown on every
  install, so the Options item is no longer hidden when the app registers no
  org-set switch. A support session is told it cannot see or set the
  language: it has no membership to read `GET /api/v1/orgs/[id]` with, and
  the route refuses it.
- **API text stays English.** A refusal or confirmation the page shows from a
  route (`err.message`) reads as the route wrote it. Where the page has its
  own sentence for an outcome it uses that: the member invite's confirmation,
  and a waitlist refusal (`admin.waitlist.refusals`, held to
  `WAITLIST_INVITE_REFUSAL_MESSAGES` by a test).
- `SUPPORT_GRANT_LEVEL_LABELS` stays as the English for the staff screens
  that name a grant's level.

## Writing a string

```tsx
// Server Component
import { getTranslations, getFormatter } from 'next-intl/server';

const t = await getTranslations('common');
const format = await getFormatter();
<p>
  {t('save')} · {format.dateTime(createdAt, 'short')}
</p>;

// Client Component
import { useTranslations, useFormatter } from 'next-intl';
```

Keys are type-checked against `en.json` (`types/next-intl.d.ts`), so a typo
fails `npm run type-check`. Plurals, selects and rich text are ICU:
`"{count, plural, one {# item} other {# items}}"`.

Named formats: `dateTime` `short` (20 Nov 2026), `long`, `dateTime`, `time`;
`number` `decimal`, `percent`, `compact`. Money is
`format.number(n, { style: 'currency', currency })`.

## Form validation messages

A schema a form shows has a factory that takes a translator; the exported
constant is the same schema in the source English, which is what an API
route returns, so API error text never depends on who asked.

```tsx
const tv = useTranslations('validation');
const schema = useMemo(() => createSignInSchema(tv), [tv]);
```

The factories are in `lib/validations/{auth,user,contact}.ts`, and for the
org-settings forms `createInviteOrgMemberSchema`, `buildSupportGrantSchema`
and `createSaveProviderKeySchema` in `lib/validations/tenancy.ts`;
`buildWaitlistDetailsSchema(fields, t)` takes one too (a fork's field label
goes in as given). `ValidationT` and `englishValidation` are in
`lib/validations/messages.ts`. Limits are written into the messages
(`at least 8 characters`) rather than passed as `{min}`: ICU groups a
number argument (`5,000`), which would change the API's text.

An app's `overridePlatformMessages('en', { validation: … })` changes what a
form shows, but not an API route's error text. `englishValidation` reads
`en.json` directly, because the exported schemas are built when the module
loads, in the browser as well as the server, where the app's overrides are
not registered. To change an API's validation text, build the route's schema
from a factory with your own `ValidationT`.

## Tests

`tests/setup.ts` mocks `next-intl` and `next-intl/server` with the real
source catalogue (`tests/helpers/i18n.ts`), so a component test renders the
English a viewer sees with no provider, and a key missing from `en.json`
fails it. A test that needs another locale mocks the module itself.

The `next-intl/server` mock loads the client mock first. Without that, a
server page test that renders a real client component got the real
`useTranslations` and failed with no provider: the server mock's helper
import built the client mock half-way (t-1074).

## Emails

An email has no request, so the send site works out the language from who
receives it and renders the template and the subject in it before calling
`sendEmail()`, which takes no locale. The visitor cookie and
`Accept-Language` do not apply: the mail is read later, somewhere else.

| Recipient                                                                     | Language, first that is supported wins                                               | Time zone       |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------- |
| A user (`emailLocaleForUser(userId)`)                                         | their own choice; their org's default; `en`                                          | `User.timezone` |
| An invitee (`deliverInvitation`)                                              | their account's own choice, if the address has one; the inviting org's default; `en` | theirs, or UTC  |
| A waitlist entry                                                              | the language it was joined in (`WaitlistEntry.locale`); its org's default; `en`      | UTC             |
| A configured address (contact form, escalation, workflow, event subscription) | the org's default (`emailLocaleForOrg`; the install org for the contact form); `en`  | UTC             |

A new user has made no choice of their own yet, so their verification and
welcome emails follow their org's default, not the language they were
browsing in when they signed up.

"Their org" is the one a sign-in starts them in (`sessionOrgOf()` in
`lib/tenancy/membership.ts`), or the org their signup recorded when the
membership is not written yet. A failed read is logged and the email goes in
English rather than not at all.

```ts
import { emailLocaleForUser } from '@/lib/email/locale';
import { emailTranslator } from '@/lib/email/translate';

const where = await emailLocaleForUser(user.id); // { locale, timeZone }
await sendEmail({
  to: user.email,
  subject: emailTranslator(where, 'emails.welcome')('subject', { brand: BRAND.name }),
  react: resolveEmailTemplate('welcome', props, where),
});
```

- **Strings** are under `emails.<kind>` in `en.json`, subjects as
  `emails.<kind>.subject`. An app changes one with
  `overridePlatformMessages()`, like any platform string.
- **Templates** get `locale` and `timeZone` as props. `resolveEmailTemplate`
  passes them to the platform default and to an app's override alike; an
  override that ignores them renders in English, as before. Translate with
  `emailTranslator({ locale, timeZone }, namespace)` and set
  `<Html lang={locale}>`.
- **Dates** use `emailDateTime()` (the named `dateTime` format, with the zone
  named) and `emailDate()` (`long`), from `lib/email/translate.ts`.
- **A workflow notification's** subject and body are its author's, so only
  the email's own frame is translated. An event email's payload fields are
  shown as the event names them, as a webhook receiver gets them.
- **An app's own email kind** (declared on `EmailPropsMap`) gets the locale
  the same way, and reads its strings with
  `emailTranslator(where, 'app.emails.<kind>')`.

`tests/unit/emails/pseudo-locale.test.tsx` renders every template in
`emails/` under the pseudo-locale and fails on English left in it. A template
added to `emails/` without a case there fails it too.

## An app's own strings and languages

An app registers from `initAppMessages()` in `lib/app/messages.ts`, with the
functions in `lib/i18n/registry.ts`. The registry runs it once, lazily,
before the first catalogue or supported-locale read. Only the server reads
it, for catalogues and the locale schemas on API routes. Keep the registry
and `supportedLocales()` off the client, because they bring the catalogue, every
translation the app registers and the ICU parser. A client form checks only
a tag's shape (`isLanguageTag` from `lib/i18n/tags.ts`, which imports
nothing) and the route checks that the locale is supported. Client components
get their messages from the server.

| Call                                        | Does                                                                                                                    |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `registerAppMessages(locale, { app: … })`   | Adds the app's own strings in `en` or a registered locale. Top-level keys must be `app` (or `framework`, for that tier) |
| `registerAppLocale(tag, platformStrings)`   | Adds a language: supported at once, for users, orgs and visitors. `platformStrings` is the platform's strings in it     |
| `overridePlatformMessages(locale, strings)` | Replaces individual platform strings in `en` or a registered locale                                                     |

```ts
// lib/app/messages.ts
import appEn from '@/lib/app/messages/en.json'; // { "app": { "client": { "title": "Clients" } } }
import platformFr from '@/lib/app/messages/platform-fr.json'; // { "common": { "save": "Enregistrer" } }
import appFr from '@/lib/app/messages/fr.json';
import {
  overridePlatformMessages,
  registerAppLocale,
  registerAppMessages,
} from '@/lib/i18n/registry';

export type AppMessages = typeof appEn; // t('app.client.title') type-checks

export function initAppMessages(): void {
  registerAppMessages('en', appEn);
  registerAppLocale('fr', platformFr);
  registerAppMessages('fr', appFr);
  overridePlatformMessages('en', { common: { save: 'Save changes' } });
}
```

Then `const t = await getTranslations('app.client'); t('title')`.

**Merge order.** Each layer wins over the one before:

1. the source, `en`: the platform's strings, then the app's `en` strings,
   then the app's `en` overrides;
2. the locale's platform translations and the app's strings in it;
3. the locale's overrides.

The pseudo-locale is generated from the source, so it shows app strings and
`en` overrides too.

**A key a locale lacks** shows in English, per key. When that locale's
catalogue is built, the log gives the number of missing keys and names up to
20 of them, once per locale and count
(`i18n: strings missing from an app locale show in English`).

**A platform key the platform does not have** (retired in an upgrade, or a
typo) is dropped from a translation or override with a warning, not thrown,
so an upgrade that removes a string never takes a whole translation down.

**What throws**, and so rolls back every registration and leaves the
platform catalogue serving: a tag that is not a language tag, or a deprecated
one `Intl` renames (`iw`, use `he`); a key that is a string in one call or locale
and a group of strings in another; `en` or
`en-XA` passed to `registerAppLocale` (override those instead); strings for
the pseudo-locale, or for a locale not yet registered; a namespace other than
`app` / `framework` in `registerAppMessages`, or either of those anywhere
else; a value that is not an object of strings; a string that is not valid ICU
(`'Hi {name'`); a key with a `.` in it.
Tags are stored canonical (`pt-br` → `pt-BR`).

## Checking a screen

Set your own language to `en-XA` (`PATCH /api/v1/users/me`
`{ "locale": "en-XA" }`), or as a visitor `PUT /api/v1/locale`. Every catalogue
string then reads `[Åççéñţéð]`. Plain English left on the page did not come
from the catalogue. Text cut off before its `]` has no room to grow, and
real translations run longer than English.

## Rendering cost

Resolving the locale reads cookies, headers and the session, so rendering is
dynamic. That changed nothing: the root layout already read `headers()` for
the CSP nonce, so no page was static before.

It does add work to **every** page render, public and marketing pages
included: the root layout's `getLocale()` resolves the session and, for a
signed-in viewer, enters the org they act in (`requestPrincipal()`), then reads
their user row and that org's settings. All of it is cached for the request
and shared with anything else on the page that asks. A visitor with no session
cookie costs no database read. If the reads fail, the page still renders in the
browser's language and the log says `i18n: could not read the viewer's
language preferences`.

## The global error page is English

`app/global-error.tsx` replaces the root layout when that layout itself
throws, so the request config may be what failed. It renders its own
`<html lang="en">` with literal English on purpose, and stays that way: on
`en-XA` it is the one page expected to show plain English.
